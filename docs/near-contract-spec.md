# School Fee Registry: NEAR contract specification

Status: final specification with your confirmed values. No contract code has been written.

## 1. Goal
A small, fixed (non-upgradeable) NEAR contract that registers school fee invoices and records a payment when a parent pays the exact amount in USDC. The USDC is forwarded straight to the school treasury. The contract never keeps funds.

## 2. Actors and trust model
| Actor | Account | Powers |
|---|---|---|
| School admin | One NEAR account, set at deploy | Create invoices, cancel unpaid invoices |
| Treasury | `bd73e625f18d762274625333c5200aae67d0ec65d09797b27118a06c24dc6669` | Receives all USDC. No powers over the contract |
| Parent / payer | Any NEAR account | Pays an open invoice with the exact amount |
| USDC token contract | One NEP-141 token account, set at deploy | Only this token is accepted |

The admin cannot move parent funds, change the treasury, or change the token after deploy. Nobody can upgrade the code.

## 3. Configuration (set once at init, immutable)
- `admin`: `mouseng20.testnet`
- `treasury`: the implicit account above
- `usdc_token`: `3e2210e1184b45b64c8a434c0a7e7b23cc04ea7eb7a6c3c32520d03d4afcb8af` (NEAR testnet USDC, NEP-141)

## 4. Storage
Per invoice, keyed by `invoice_id` (a random 32-character lowercase hex string generated by the backend, also used in the public payment link):
- `amount`: u128 in the token's smallest unit (USDC uses 6 decimals)
- `due_date`: u64 timestamp, informational
- `status`: Pending, Paid, or Cancelled
- `payer`: account ID, set when paid
- `paid_at`: u64 timestamp, set when paid

No student names, terms, or line items are stored onchain. Those stay in the backend database.

## 5. Public methods
| Method | Caller | Behavior |
|---|---|---|
| `new(admin, treasury, usdc_token)` | Deployer, once | Initializes config. Fails if already initialized |
| `create_invoice(invoice_id, amount, due_date)` | Admin only | Fails if the ID exists or the amount is 0. Stores a Pending invoice. Emits `invoice_created` |
| `cancel_invoice(invoice_id)` | Admin only | Only Pending invoices. Sets Cancelled. Emits `invoice_cancelled` |
| `ft_on_transfer(sender_id, amount, msg)` | USDC token contract only | `msg` is the `invoice_id`. See payment flow below |
| `register_treasury()` | Admin only, payable | Calls `storage_deposit` on the USDC token for the treasury with `registration_only = true`, using the attached NEAR. Safe to call again: the token keeps the deposit already made. Emits `treasury_registered` |
| `get_invoice(invoice_id)` | Anyone (view) | Returns the invoice or null |
| `get_config()` | Anyone (view) | Returns admin, treasury, usdc_token |

## 6. Payment flow
1. Parent's wallet calls `ft_transfer_call` on the USDC contract with receiver = fee contract, the amount, and `msg` = `invoice_id`.
2. USDC calls `ft_on_transfer` on the fee contract.
3. The contract checks all of these. If any check fails, it returns the full amount, which refunds the parent automatically:
   - the caller is the configured USDC token
   - the invoice exists and is Pending
   - the amount equals the invoice amount exactly
4. If the checks pass, the contract calls `ft_transfer` on USDC to send the amount to the treasury, then runs a callback.
5. The callback marks the invoice Paid, saves payer and time, and emits `invoice_paid` only if the forward succeeded. If the forward failed, the invoice stays Pending and the full amount is refunded.
6. The backend watches `invoice_paid` events and shows the transaction reference on the dashboard and in the CSV.

An invoice is marked Paid only after the treasury transfer succeeds. Two simultaneous payments cannot both succeed, because the status check and the status change happen under the same invoice record. The callback re-checks Pending before it writes Paid. If it finds the invoice already Paid or Cancelled, it refunds.

## 7. Events (NEP-297 style JSON logs)
`invoice_created`, `invoice_paid` (invoice_id, payer, amount, timestamp), `invoice_cancelled`.

## 8. Failure modes and handling
| Case | Result |
|---|---|
| Wrong amount (over or under) | Full refund, invoice stays Pending |
| Unknown or already paid or cancelled invoice | Full refund |
| Wrong token sent to the contract | Rejected, because only `usdc_token` can trigger `ft_on_transfer` |
| Treasury not registered with the USDC token | Prevented by setup: the admin dashboard checks the treasury's registration (`storage_balance_of` on USDC) and shows a required "Activate payments" step that calls `register_treasury`. Invoices cannot be shared until it shows Ready. If registration is ever missing, the forward fails and the parent is fully refunded |
| Payment arrives after due date | Accepted. Due date is display-only, and the dashboard shows Overdue |
| Duplicate invoice ID | `create_invoice` fails |

## 9. Threat model
- Only the admin can create or cancel invoices (checked against the caller's account).
- Only the USDC token contract may call `ft_on_transfer`, so nobody can fake a payment.
- A fake token cannot be used, because the token account is fixed at init.
- Refund logic relies on the NEP-141 rule that the return value of `ft_on_transfer` is the unused amount.
- Reentrancy is handled by setting state in the callback only, with a second Pending check.
- Admin key loss: invoices can no longer be created or cancelled, but existing payments and the treasury are unaffected. Use a hardware-backed key or multisig account for the admin.
- Parent privacy: only an opaque ID and the payer account appear onchain.

## 11. App around the contract
- **Parent page** `/pay/:invoiceId`: shows invoice details from the backend, connects a NEAR wallet, and sends the payment. Simple wording ("Pay school fees", "Payment received").
- **Admin dashboard** `/admin`: NEAR wallet sign-in as `mouseng20.testnet`, a setup checklist (treasury registered, contract live),  invoice table with status and transaction reference, create-invoice form, and CSV export.
- **CSV columns**: invoice number, student ID, student name, term, amount (USD), due date, status, paid date, payer account, transaction reference. Plain headers, ISO dates, no currency symbols.
- **Backend**: stores invoice details, verifies payments from chain data, and never marks anything Paid on a browser's say-so.
- **Branding**: none. The Arc Studio watermark is removed from the app shell.

## 12. Testing plan
